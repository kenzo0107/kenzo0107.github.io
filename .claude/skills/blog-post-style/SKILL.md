このブログ（Hexo, `_blog/source/_posts/`）の過去記事を分析して得た、筆者固有の書き方のパターン。新しい記事を書くときはこれに沿う。迷ったら過去記事に実例があるので `_blog/source/_posts/` を grep して確認する。

## 1. ファイルと Front Matter

- 1記事 = 2ファイル。日本語 `YYYY-MM-DD-slug.md` と英語 `YYYY-MM-DD-slug-en.md` を必ずセットで作る（このブログは全記事バイリンガル運用）。
- `translation_id` は日英で同じ値（= slug）。英語側だけ `lang: en` と `permalink: en/YYYY/MM/DD/slug/` を追加する。
- カテゴリは技術ドメイン基準（AWS, Go, Terraform, Database, Monitoring, Infrastructure, RaspberryPI, Data Analytics, DIY, AI 等）。単一なら `category: X`、複数なら
  ```yaml
  categories:
  - [Monitoring]
  - [AI]
  ```
  の形（配列の配列）。`AI` カテゴリは「AI が主役のネタ（AI で全部作った個人開発、AI活用の効果検証など）」に使う。技術ツールの記事は AI 支援で作っていてもドメインカテゴリ（Go / Terraform 等）を優先し、`AI` は補助的に付ける程度。
- `tags` はプロダクト名・技術名を具体的に（例: `[AWS, Aurora, CDC, CloudWatch, MySQL, PostgreSQL]`）。
- `cover` は2種類ある。外部画像（GitHub raw / imgur）をそのまま貼るか、`/img/cover/<slug>.svg` を使う。後者は `_blog/gen-covers.js` が生成するデザイン。新規記事では基本 `/img/cover/<slug>.svg` を使い、既存 SVG のグラデーション×ドットパターンのスタイルを踏襲する（配色はトピックのハッシュ/キーワードで hue を決めている）。日英で同じ SVG パスを共有する（英語版だけの SVG は作らない）。
- ToC が要る長さ・比較記事では本文の先頭にこれを入れる（任意、必須ではない）:
  ```html
  <div class="toc">
  <div class="toc-content">
  <h3 class="menu-label">ToC</h3>
  <!-- toc -->
  </div>
  </div>
  ```

## 2. 冒頭（リード文）

- 最初の1〜3文で「何をしたか / 何を作ったか / 何を比較したか」を言い切る。前置きなしで結論から入る。
- 時点情報が重要な調査記事（料金・仕様比較など）は `※ 本記事は **YYYY年M月D日時点**の調査です。...` のような注意書きを入れる。
- そのあとに `<!-- more -->` を置く。

## 3. 見出し構成の型

記事の性質によって型が決まっている。だいたいこの2パターン。

**A. 「作った」系（OSS・個人開発の紹介）**
```
## 概要 / 作った背景
## （課題・既存手段の限界）
## どんなツールか / 主な特徴
## 使い方
## 実装のポイント・技術メモ
## （デメリット・注意点・今後の展望）
## まとめ / おわりに
```

**B. 「比較・調査」系**
```
## 結論          ← 表で要約を先出し
## 比較表        ← 観点 × 対象の表
## 対象Aの詳細（メリット/デメリット、参考リンク）
## 対象Bの詳細（メリット/デメリット、参考リンク）
## 料金比較
## まとめ
## 参考           ← 参照した一次情報のリンク集
```

どちらの型でも、最後は「まとめ」または「おわりに」で箇条書きの再要約。調査系記事は最後に「参考」で一次情報（公式ドキュメント・GitHub）のリンクを列挙する。

## 4. 文体のクセ

- 一人称の体験談。「〜を作るに至った話です」「〜作りました」「〜が知りたく」「〜に困ったので」など、動機を必ず書く。
- 「確認できず」「確認できました」「明記されています」など、**一次情報で確認したかどうか**を明言する。裏取りできていないことは正直に「（公式に明確な記載を確認できず）」と書く。何かを主張したら根拠（公式ドキュメントURL、GitHub の README/PR）を示すか、確認できなかったと明言する。
- 断定を避けたい箇所は「〜ではないか、という推察」「〜かもしれません」を使うが、多用しない。
- 太字 `**...**` は文中のキーワード強調に使う（見出しではなく地の文の中で）。多用してよいが、1文に1箇所程度に留める。
- 箇条書きを多用する。3項目以上の並列情報は文章で書かず箇条書きにする。
- 比較・対応関係は表にする（Markdown table）。観点を行、対象を列にするのが基本。
- コードブロックは実際に動くコマンド／HCL／出力例をそのまま貼る。説明のための省略記法ではなく実物を使う。
- デメリット・限界・スキップしたことは隠さず書く。「デメリット」「注意点」「もっとこうなったらいいのに」のような見出しを立てて正直に書く。できなかったこと・試していないことは「〜のため確認できていません」「〜は未対応です」とはっきり書き、代わりに濁したり誇張したりしない。
- 締めの一文はシンプルで謙虚。「以上です。ご利用いただけますと幸いです。」「参考になれば幸いです。」「よければ触ってみてください。」など。
- リポジトリへの言及は文中リンク＋末尾に改めて `- リポジトリ: [owner/repo](https://github.com/owner/repo)` を置く。
- 長い一文の途中で改行したいだけの場合、Markdown 段落を割らずに `<br/>` を使うことがある（箇条書きや見出しほど改まった構造にしたくない小さな補足のとき）。

## 5. 英語版の作り方

- 日本語版の直訳ではなく自然な英語だが、**見出し構成・表・コードブロック・リンクは1対1で対応**させる。文の量やトーンも揃える（謙虚な言い回しは英語でも "I hope this helps" 程度に軽く訳す）。
- 製品名・リソース名・コマンドはそのまま英語版にも残す。
- Front matter の `title` は英語で意味が通る自然なタイトルにする（日本語タイトルの逐語訳でなくてよい）。

## 6. 実務上のチェックリスト（新規記事作成時）

1. 過去に似たテーマの記事がないか `_blog/source/_posts/` を grep する
2. 一次情報（公式ドキュメント・GitHub README/docs・実装コード）にあたり、確認できたこととできなかったことを分けてメモする
3. 型（A: 作った系 / B: 比較系）を決めて見出しを先に立てる
4. 日本語を書く → 見出し・表・コード構成をそのまま使って英語版を書く
5. `category`/`categories`・`tags`・`cover` を Front matter に設定する
6. `_blog/CLAUDE.md` の開発コマンド（`npm run build` 等）はローカルで軽く確認する程度に留め、実際のビルド・デプロイは指示があるまで行わない
